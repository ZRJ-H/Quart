# 每日知识采集与分层摘要设计

## 背景

当前仓库只有 GitHub Trending 的自动采集工作流。AI 科技动态、时政要闻、AI 论文日报和 Hacker News 的最新内容停留在 2026-06-27，并被 Quartz 的 7 天过滤器从线上构建中移除，因此对应栏目路径返回 404。首页周报链接还硬编码到 `2026-W25`。

目标是在 2026-09-11 首次生成当天内容，之后每天自动采集、整理、提交并部署；当天无足够内容时允许回溯最近 48 小时，但必须标明原始发布时间。

## 方案选择

采用单一 `Collect Daily Knowledge` GitHub Actions 工作流统一处理五个日报栏目。相比每栏目独立工作流，它只产生一次内容提交和一次 Pages 部署，同时通过独立采集适配器隔离数据源故障。相比付费新闻 API，它优先使用无需密钥的公开官方接口，现有大模型密钥只用于可选的中文整理。

## 数据源

- **GitHub Trending**：复用现有 GitHub Search API 采集器与项目增量逻辑。
- **Hacker News**：使用官方 Firebase API 的 top stories 与 item 接口，保留分数、评论数、原文和讨论链接。
- **AI 论文**：使用 arXiv Atom API，查询 `cs.AI`、`cs.LG`、`cs.CL`，以提交时间排序并去重。
- **AI 科技**：聚合多个 AI 机构的官方 RSS/Atom 源；源列表配置化，一个来源失败不阻断其他来源。
- **时政要闻**：聚合多个公开权威新闻 RSS/Atom 源；源列表配置化并保留媒体名称与原始链接。

所有网络请求设置明确的 User-Agent、超时和有限重试。解析器只接受 HTTP(S) 链接，清理 HTML，按规范化链接和标题去重。

## 时间和选取规则

- 工作流每天北京时间 08:30（UTC 00:30）运行，并支持手动触发。
- 文件名和归档日期使用 `Asia/Shanghai`。
- 优先选择运行日发布的内容；不足目标条数时回溯最近 48 小时。
- AI 科技 8 条、时政 8 条、AI 论文 5 篇、Hacker News 8 条；GitHub Trending 保留现有 25 项上限。
- AI 科技与时政至少各 3 条，AI 论文至少 3 篇，Hacker News 至少 5 条。低于下限时该次采集失败，不写空白或伪造日报。
- 对同一天重复运行必须幂等：内容没有变化时不产生提交，有变化时原子替换当天文件。

## 分层摘要

每个日报先给出来源覆盖、回溯窗口和关键词，再按重要性排序：

- 前 3 条使用 250–400 字深度摘要，包含可核对事实、必要背景、关键数据、潜在影响和后续观察点。
- 其余条目使用 80–150 字精简摘要，包含核心事实、来源、原文链接和明确价值点。
- 文末给出 3 条“今日趋势判断”，并把来源事实与编辑性推断分开标注。
- 禁止仅改写标题、重复套话、无来源数字和无依据的“重大突破”等判断。

不同栏目增加专用字段：

- AI 论文：研究问题、方法、实验结果、局限、工程价值和 arXiv 链接。
- Hacker News：分数、评论数、原文链接、讨论链接和社区讨论焦点。
- 时政：事件主体、时间地点、政策或市场影响，避免把预测写成事实。
- AI 科技：产品/研究变化、可验证指标、适用对象和产业影响。

## 摘要生成与降级

采集器先生成结构化 JSON，再交给摘要器。若 `DEEPSEEK_API_KEY` 或 `GO_API_KEY` 可用，则模型只能依据结构化输入生成中文 Markdown，不允许补充输入中没有的事实；提示词要求保留原始链接、日期和数字。模型不可用、超时或输出校验失败时，使用确定性模板将源标题和摘要直接写入 Markdown，保证采集链路不依赖模型成功。

输出校验检查目标条数、标题、发布日期、HTTP(S) 链接、必要字段和禁止的空占位符。校验失败不会覆盖已有日报。

## 工作流与部署

现有 `collect-github-trending.yaml` 扩展并改名为 `Collect Daily Knowledge`：

1. 安装 Node.js 与 Python 运行环境。
2. 运行统一采集脚本，生成四个新增日报和 GitHub Trending 日报。
3. 校验所有输出并提交 `content/`。
4. 使用默认 `GITHUB_TOKEN` 推送一次内容提交。

`deploy.yaml` 的 `workflow_run` 监听名称同步改为 `Collect Daily Knowledge`。采集工作流成功后即使内容提交由默认令牌创建，也会触发 Pages 构建；失败则保留上一次正常站点。

首次合并采集器时通过受限 `push.paths` 触发一次立即采集，之后仅由 schedule 或手动运行触发，避免内容提交造成循环。

## 页面与周报

Quartz 保留 7 天日报过滤策略，因为每日采集恢复后栏目会持续存在。首页五个栏目继续指向文件夹页；周报入口改为 `[[周报|浏览全部]]`，不再硬编码旧周次。

每周一根据最近七天已提交日报生成周报；首次上线时生成当前周的截至今日汇总。周报只综合仓库内已有日报并回链原文，不再次抓取外部信息。

## 测试与验收

- 使用本地 RSS、Atom、HN JSON 固定样本测试真实解析行为，不在单元测试中访问网络。
- 覆盖日期边界、48 小时回退、去重、最低条数、HTML 清理、URL 校验、幂等写入和失败不覆盖。
- 测试 Markdown 输出的栏目专用字段、分层摘要字数区间和来源链接保留。
- 测试工作流的计划任务、首次触发、权限、单次提交以及 Pages `workflow_run` 名称。
- 运行一次真实网络采集，检查五个当天文件和当前周周报，再完成 Quartz 生产构建。
- 推送后确认 Actions 采集与部署均成功，并逐个检查六个栏目入口、当天页面、内容索引和搜索索引返回 HTTP 200。

## 非目标

- 不引入付费新闻服务。
- 不自动发布未经来源数据支持的内容。
- 不重构现有 Cloudflare 搜索 Worker。
- 不修改历史日报正文。
